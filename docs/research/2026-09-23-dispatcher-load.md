# Разгрузка диспетчера — ресёрч

23.09.2026. Вопрос: диспетчер перегружен? Оставить ему только сессии, ветки и связь, план
отдать сессии пункта, вопросы по проекту — отдельной сессии «арбитр/куратор»?

## 1. Замер: чем реально занят диспетчер

|---|---|---|
| сообщений человека → диспетчеру | 68 | 128 |
| сообщений сессий → диспетчеру | 187 | 3 |
| автокомпактов | 3, каждый на ~667k токенов | 3, на 648–669k |
| контекст хода API, медиана | 338k | 378k |

| вызовов: механика git/сессий + правка роадмапа + связь | 54% | 22% |
| вызовов: прод-операции (`docker`, `ssh`) | 268 (17%) | — |
| вызовов: правка кода, README, docs | 2% | 21% |

17 — диспетчер висел на `AskUserQuestion`** (два вопроса: «удалить 5 пустых карточек» и «F-6:
меняем приёмку»), и до ответа человека стояла вся очередь. Одно — долгий `docker` в цикле.

**Вывод по замеру.** В reinhold диспетчер в основном делает свою работу (больше половины
вызовов — механика и связь), но сверху висят прод-операции и ответы. В mast «диспетчер» был
основной рабочей сессией: 3 сообщения от сессий, 202 правки кода и README, ресёрч под новые
пункты. Раздутие контекста реальное в обоих: три компакта за 2–3 дня. Причём метод уже
держит состояние вне контекста («перезапуск ничего не теряет») — и перезапуском не пользовались.

## 2. Факты нашей схемы

- **Имя сессии на пункте фиксируется.** Слот строки `ROADMAP.md`: `` `worktree-A-1` · сессия `A-1` · с 15.09 ``;
  имя = номер пункта через `--name`, пометку ставит диспетчер до старта. В `STATUS.md` имени нет.
  id для `claude attach` не пишется — его даёт `claude agents`.
- **`STATUS.md` — владение поделено.** Признаки видны при запуске — шапку заводит диспетчер
  («Запуск пункта», шаг 2), появились по ходу — сессия (`…-item.md` §1); план задачами всегда
  пишет сессия через `writing-plans`. Шапка сама по себе не проблема. Обоснование «до старта,
  иначе worktree не увидит» верно для строки `ROADMAP.md`, но не для `STATUS.md`: он может
  родиться в ветке пункта.
- **Проблема в содержимом.** В reinhold 40 запусков `claude --bg`, промпт — медиана 1165
  символов: состояние `master`, соседи, окна на прод. А в шапку `STATUS.md` (генерировалась
  Python-вставкой из Bash, ~3,4k символов) диспетчер писал проектные указания: «сторож делай не
  в `doctor.py`, а тестом». Это решение пункта, принятое без чтения кода, — место ему в строке
  пункта как ограничение или нигде.
- **Попутно: линт обходится.** Тот же Python переписывал `ROADMAP.md` через Bash — хук
  `PostToolUse` видит только Edit/Write. Правило «правь Edit, не `sed`» — проза без guard.
- **«Арбитр» в reinhold — другое.** `reinhold-arbiter` и `reinhold-fixer` — контур мониторинга
  бота (арбитр раз в час пишет журнал, исполнитель чинит), а не консультант по проекту.
  Предложенный куратор не испытан.

## 3. Что есть в Claude Code прямо сейчас (проверено по документации)

- **`/btw`** — побочный вопрос: видит весь разговор, **в историю не попадает**, инструментов нет,
  при тёплом кэше почти бесплатен. `f` в оверлее — форк в фонового субагента с инструментами.
  Документация: «use `/btw` to ask about what Claude already knows from this session; use a
  subagent to go find out something new». [interactive-mode#side-questions-with-btw](https://code.claude.com/docs/en/interactive-mode.md)
- **Agent Teams: план пишет исполнитель.** Тиммейт в plan mode пишет план, лид одобряет. Лиду
  документация советует давать контекст в промпте старта, а не план. И сама признаёт наш
  симптом: «Sometimes the lead starts implementing tasks itself instead of waiting for teammates».
  [agent-teams](https://code.claude.com/docs/en/agent-teams.md)
- **`SendMessage` с `notify_when_idle`** — одно уведомление, когда сессия освободится, без
  опроса. Скрипт или хук может писать в сессию через `CLAUDE_CODE_MESSAGING_SOCKET`. Очередь
  входящих — до 50, сообщение читается между вызовами инструментов.
  [cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging.md)

## 4. Как это разделено у других

| Решение | Разговор с человеком | Кто пишет план | Кто вливает | Кто следит за исполнителями |
|---|---|---|---|---|
| [Gas Town](https://github.com/steveyegge/gastown) | Mayor | Mayor заводит задачи (beads, convoys) | **Refinery** — отдельный агент, очередь мерджей с проверками | Witness (по репозиторию), Deacon (патруль) |
| [Anthropic: long-running harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | — | initializer-сессия один раз пишет список фич; кодинг-сессии меняют только поле `passes` и сами планируют свой шаг | сессия коммитит сама | прогресс-файл + `git log` |
| [Agent Teams](https://code.claude.com/docs/en/agent-teams.md) | лид (или напрямую с тиммейтом) | тиммейт в plan mode, лид одобряет | — | лид, уведомления о простое |
| [OpenAI Symphony](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md) | трекер задач | исполнитель: «Start work by writing/updating a hierarchical plan in the workpad» | исполнитель сам, после Human Review | статусы задачи в трекере |
| [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md) | — | был отдельный Scrum Master, пишущий story для dev-агента; в v6.3 **упразднён**, влит в Developer | — | — |
| [Cursor, scaling agents](https://cursor.com/blog/scaling-agents) | — | планировщики декомпозируют, «как» — исполнитель | integrator **убрали**: «created more bottlenecks than it solved» | периодический fresh start |

**План.** Везде, где нашлось, координатор или планировщик пишет «что» и «когда готово», а «как»
— исполнитель, изучив код. Anthropic прямо предупреждает: если планировщик заранее задаёт
технические детали и ошибается, «the errors in the spec would cascade»
([harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
Единственный найденный отдельный автор задач для исполнителя — Scrum Master в BMAD — упразднён.
Cognition среди провалов схемы «менеджер раздаёт» называет «overly prescriptive managers».

**Вливание.** Отдельный агент-мерджер есть только в Gas Town на 20–30 исполнителей. Cursor от
integrator отказался; в Symphony, у OpenAI и в Conductor вливает исполнитель или человек.

**Консультант.** Oracle и Librarian в Amp и oh-my-opencode, `explorer` в Codex, «Smart Friend» у
Cognition — **везде разовый субагент на чтение**, со свежим контекстом, возвращает сводку.
Долгоживущего «знатока проекта» не нашлось ни у кого. Crew в Gas Town — рабочее место
человека, а не справочная.

**Чистый контекст координатора.** Состояние вне контекста и перезапуск вместо сжатия: «sessions
are cattle» в Gas Town, «periodic fresh starts to combat drift» в Cursor, сброс контекста со
структурированной передачей у Anthropic. Роль держится механизмом, а не текстом: в Gas Town
PreToolUse-хуки запрещают Edit/Write координатору — «from instructions to machinery»
([witness-at-team-lead](https://github.com/steveyegge/gastown/blob/main/docs/design/witness-at-team-lead.md)).

**Цена разделения.** Google/MIT: при центральном координаторе ошибки усиливаются в 4,4 раза, у
независимых агентов — в 17,2; на делимых задачах +81%, на последовательных −39…−70%
([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)). Cognition: схема работает, когда «writes
stay single-threaded and the additional agents contribute intelligence rather than actions».

**Главное: Gas Town делит ровно наоборот.** У Mayor остаются разговор с человеком и
постановка задач, а уносится механика — мерджи в Refinery, здоровье исполнителей в Witness.
По разбору [Maggie Appleton](https://maggieappleton.com/gastown), узкое место там — не
исполнение, а дизайн и планирование: «it's always the design».

*Не проверено:* посты Yegge на Medium (403), цитаты по Gas Town — из репозитория и разборов.
*К слову:* таксономия провалов multi-agent систем из Беркли тоже называется MAST
([arXiv 2503.13657](https://arxiv.org/abs/2503.13657)) — коллизия имени.

## 5. Разбор предложения

**«Диспетчеру — только сессии, ветки, связь».** Наполовину. Дрейф идёт не от текста скилла, а
от того, что диспетчер — единственное окно человека в проект: туда несут всё. Но унести от него
разговор — значит поставить куратора между человеком и состоянием: на «что от меня надо» и
«что за G-10» куратор ответит, только спросив диспетчера, и появится ещё одно звено пересылки
(на пересылку человек уже жаловался). Gas Town решает наоборот: разговор и постановка задач
остаются у координатора, механика уезжает. Для нас механика детерминирована, поэтому ей нужен
не агент-Refinery, а скрипт. Остаток — чтение файлов под ответы (34–58% байт результатов) —
уходит в субагентов: в контексте диспетчера остаётся вывод, а не файлы.

**«План пишет сама сессия».** Да. Совпадает с Agent Teams, с `superpowers:writing-plans` и с
нашим же скиллом сессии пункта. Но у диспетчера остаётся **контракт**, а не план: строка
`ROADMAP.md` — описание, `Мои пути`, `Зависит от`, «Готово когда» с числом. Реальный риск —
не план, а **контекст разговора с человеком** (зачем пункт, какие варианты отвергнуты): сейчас он
едет в эфемерном промпте старта и теряется. Место ему — строка пункта: она читается сессией и
переживает перезапуск. Промпт старта — шаблон: номер, ссылка на скилл, только
координационные факты (соседи по путям, окна на общие ресурсы, что сдвинулось в `main`).

**«Арбитр/куратор для вопросов».** В виде долгоживущей роли — нет (раздел 4). Вопросы человека трёх видов, и решаются по-разному:

| Вопрос | Пример | Куда |
|---|---|---|
| о состоянии, которое диспетчер знает | «что от меня надо», «что за G-10», «итоги за ночь» | `/btw` диспетчеру; лучше — из файла (см. ниже) |
| о проекте, нужно читать код и доки | «как доезжает ядро», «где написано про sonnet» | разовый субагент диспетчера на чтение — файлы остаются в нём |
| долгое обсуждение, ресёрч, новая идея | порт на Codex, продвижение, gmail | обычная отдельная сессия, только чтение, выход — находка |

Долгоживущий куратор сам раздуется так же. Отдельная сессия под длинное обсуждение — не роль,
а разовая работа с двумя ограничениями из нашего же ядра: в основной копии **только чтение**
(параллельные git-операции в одной копии откатывают чужие файлы), а результат — **находка
диспетчеру** в том же формате, что у сессий пунктов: черновик строки с «Готово когда» и числом.
Новый протокол не нужен. Решение человека, принятое в этом обсуждении, едет в той же записи.

## 6. Слабые места диспетчера, которых нет в предложении

1. **Механика — прозой, исполняется моделью каждый раз.** Вливание (ff-only, диапазон,
   проверка чистоты, уборка) и запуск (пометка строки, коммит, push, `claude --bg`) — это код.
   В reinhold механика — 23% вызовов инструментов, а запуск диспетчер переписывал ad hoc
   Python-вставкой на 3,4k символов. Скрипты `start_item`/`merge_item` — это **пол** по нашему
   же правилу: проверяемо, не устаревает с умнением модели.
2. **Правка `ROADMAP.md` мимо линта.** Хук видит только Edit/Write. Guard: проверка `ROADMAP.md`
   ещё и после Bash, если файл изменился (`git diff --quiet ROADMAP.md`), или в pre-commit проекта.
3. **«Что ждёт человека» живёт в голове диспетчера.** Спрошено 11 раз из 68; в reinhold
   появлялся ad hoc `morning.md`. Если эскалация — слот строки пункта (`ждёт человека: <вопрос>`),
   на «что от меня надо» отвечает `grep`, `/btw` или любая сессия — без контекста диспетчера.
4. **Вопрос человеку через `AskUserQuestion` останавливает диспетчера целиком.** 16 из 17
   ожиданий дольше 5 минут — отсюда, до 40 мин. Скилл говорит «пока ждёшь ответа, пункт
   продолжает работу», но модальный вопрос блокирует и вливания, и связь. Вопрос текстом (ход
   кончается, входящие будят сессию) плюс слот «ждёт человека» — очередь не стоит.
5. **Перезапуском не пользуются.** Три компакта за 2–3 дня при том, что состояние в файлах.
   Порог «контекст > N — перезапуск после ближайшего вливания» — дёшево, но это потолок.
6. **Прод-операции у диспетчера** (reinhold: 268 вызовов `docker`/`ssh`). Окно на общий ресурс
   даёт диспетчер, а выполнять — сессии пункта или отдельной ops-сессии.

## 7. Вердикт

**Ответы на вопросы.**

1. *Разгружать ли диспетчера?* Да, но главный груз — не вопросы человека, а механика прозой,
   блокирующие вопросы и прод-операции. Уточнения и «что от меня надо» — ~40% сообщений
   человека, ответы текстом — ~16% токенов.
2. *План — сессии пункта?* Да. У диспетчера остаётся контракт (строка пункта), без проектных указаний.
3. *Фиксируется ли сессия на пункте?* Да, слот «сессия» в строке `ROADMAP.md`, имя = номер пункта.
4. *Куратор для вопросов?* Долгоживущий — нет: ни у кого не нашёлся, у нас не испытан, и он
   перенесёт засорение контекста во второе место. Вместо него: `/btw` на вопросы о состоянии,
   разовый субагент на чтение для вопросов о проекте. Длинное обсуждение или ресёрч (как этот)
   — обычная отдельная сессия, только чтение, результат — находка диспетчеру. Роль под это не нужна.
5. *Слабые места* — раздел 6.

**Кандидаты — пол или потолок** (по инварианту проекта в ядро идёт только пол):

| Кандидат | Тип | Черновик «Готово когда» |
|---|---|---|
| скрипты `start_item` / `merge_item` вместо прозы в скилле | пол | вливание пункта на песочнице — 1 команда вместо N шагов; сторож: скрипт отказывает на не-ff и грязном диапазоне, 2 из 2 |
| линт `ROADMAP.md` и после правки через Bash | пол | правка строки через `python3 -c` с критерием без числа — линт вернул ошибку, 1 из 1 |
| слот «ждёт человека: <вопрос>» в строке пункта | пол | линт знает слот; «что от меня надо» отвечается `grep` — 0 обращений к контексту диспетчера |
| вопрос человеку текстом, не `AskUserQuestion` | пол, если есть хук; иначе потолок | ожиданий в очереди > 5 мин из-за модального вопроса: 16 → 0 |
| `STATUS.md` и план — только сессия пункта; промпт старта — шаблон без проектных указаний | потолок (пол — если сторож на длину/состав промпта) | — |
| вопросы о проекте — разовым субагентом на чтение, не чтением файлов в контексте диспетчера | потолок | доля байт чтения в результатах диспетчера 34–58% → < 15% |
| запрет Edit/Write диспетчеру вне `ROADMAP.md`, `DONE.md`, `TECH_DEBT.md`, `docs/roadmap/**` (как у Gas Town) | пол | правка `README.md` из сессии `*-dispatch` — отказ хука, 1 из 1 |
| перезапуск диспетчера по порогу контекста | потолок | — |

Пол из этой таблицы разобран подробно — механизмы, ограничения площадки, порядок шагов — в
[детерминированных контрактах](2026-09-23-deterministic-contracts.md).

**Открытые вопросы.**
- Как хуку узнать, что сессия — диспетчер: `session_title` есть во входе `SessionStart` (код 2.1.280, в документации не описано) — роль пишется в файл по `session_id`; у `--bg`-сессий и в Codex не проверено (см. [контракты](2026-09-23-deterministic-contracts.md)).
- Разрешить ли сессиям пунктов писать друг другу напрямую (соседи по путям), чтобы диспетчер не пересылал?
- Запрет Edit/Write диспетчеру ломает «мелкую правку вне роадмапа в основной копии» — отказ или вопрос (`ask`)?
- Скрипты вливания — в плагин (`hooks/`) для всех проектов или шаблоном в проект?
